## Context

変更の目的と対象範囲は [proposal.md](./proposal.md) を参照する。リポジトリにはOpenSpec artifact以外の実装がなく、フロントエンド、データ生成、配信を新規に構成する。

対象データは、ITSと各施設提供者が公開する複数のHTMLに分散している。料金はITSの制度ページ、施設名・住所・区分は施設提供者の一覧を根拠とするため、複数ソースを契約経路ごとに結合する必要がある。また、同じ物理施設が異なる契約経路に存在しても統合しない。公式PDFは人間による照合資料として利用できるが、自動抽出の入力にはしない。

サイトは認証や利用者データの保存を必要としない。一方、現在地取得にはHTTPSが必要であり、公開データは外部ソースのレイアウト変更や取得失敗で壊れた内容へ置き換わらないようにする必要がある。GitHub上のリポジトリとして運用することを前提とする。

## Goals / Non-Goals

**Goals:**

- バックエンドを持たない静的サイトとして、全国の対象施設をブラウザだけで表示、検索、絞り込み、距離順並び替えできる構成にする。
- 公式ソースから公開用カタログを週次で生成し、検証に成功したデータだけを配信する。
- AIを使用せず、同じ入力から同じ結果を得られる決定論的なカタログ生成処理にする。
- 地図を主役にし、管制室・テレメトリーHUDを思わせる情報密度と視認性を両立する。
- 施設ブランドと契約経路を分離し、契約経路ごとの掲載を失わずに扱う。
- 外部サービスの障害時も、直前の正常な公開データを維持できるようにする。

**Non-Goals:**

- サーバーAPI、データベース、利用者アカウント、管理画面は作らない。
- 徒歩・自動車・公共交通による経路検索や所要時間計算は行わず、直線距離だけを扱う。
- 異なる契約経路にある同一物理施設を名寄せしない。
- 施設の混雑、営業時間、設備、口コミ、ランキング、ニュースフィード、統計ダッシュボードは扱わない。
- MVPでは独自の地図タイル配信や地図スタイル編集環境を運用しない。
- カタログ生成にAI、LLM、AI-OCR、AIによる分類や補完を使用しない。

## Decisions

### 静的サイトと生成済みJSONで構成する

Vite、Vanilla TypeScript、CSSで単一画面の静的サイトを作り、GitHub Pagesへ配信する。ブラウザは同じ配信物に含まれる `gyms.json` を読み込み、検索、絞り込み、距離計算をクライアント内で行う。

```text
+--------------------+      +----------------------+      +------------------+
| ITS / provider     | ---> | Node data updater    | ---> | validated         |
| official HTML      |      | parse + normalize    |      | gyms.json         |
+--------------------+      +----------+-----------+      +--------+---------+
                                   |                           |
                                   | failure                   v
                                   +----> stop deployment   Vite build
                                                               |
                                                               v
                                                        GitHub Pages
                                                               |
                                                               v
                                                        browser + MapLibre
```

単一画面と数百件規模のデータにはReact、ルーター、状態管理ライブラリ、バックエンドは不要である。画面状態はTypeScriptの単純なオブジェクトで保持し、変更時に地図マーカーと一覧を更新する。

代替としてReactやサーバーAPIを検討したが、現時点ではコンポーネント共有、サーバー側検索、秘密情報の保持がなく、依存と運用だけが増えるため採用しない。

### MapLibre GL JSとOpenFreeMapを使用する

地図表示にはMapLibre GL JSを使用し、MVPではOpenFreeMapのDark系ベクタースタイルを利用する。地図スタイルURLは1つの定数として保持し、OpenFreeMapを利用できなくなった場合はMapLibre互換の別プロバイダーへ差し替える。

MapLibreの現在地制御、GeoJSONレイヤー、マーカー、`fitBounds`、`LngLat.distanceTo`を利用する。施設ピン、3D表示時のガイド線、ブランド名は同じGeoJSON sourceを使うviewport-alignedなsymbolレイヤーで描画し、同一の緯度経度と画面表示オフセットへ固定する。DOMオーバーレイは地図レイヤーと投影更新のタイミングが異なり視点変更時にずれるため使用しない。距離計算や3D表示のためにTurfや別の描画ライブラリは導入しない。地図タイルを直接運用する案は、MVPの利用規模に対して運用負荷が大きいため採用しない。

### 管制室・テレメトリーHUDを視覚言語にする

地図を画面全体に敷き、一覧ウィジェットと状態表示を半透明の暗色パネルとして重ねる。参考とする方向は `JAPAN CIVIL WORKS MONITOR` のような情報端末であり、画面構造や固有表現を複製せず、次の視覚原則だけを採用する。

- 等幅フォント、細い罫線、角張ったパネルを基本にする。
- 英字の短い計器ラベルと日本語の説明を組み合わせる。
- シアンを主色とし、選択、警告、料金などにマゼンタまたはアンバーを限定的に使う。
- 上部の細いステータスバーに掲載件数、現在の基準地点、最終更新日、地図のズーム・方位・傾斜を表示し、視点操作へ追従させる。
- 発光、グリッド、走査線はCSSで表現する。地図上の走査ビームと計器の状態表示は常時動かせるが、操作部を移動させず、低い不透明度と`transform`中心の描画に限定して可読性と操作性を妨げない。
- 狭い画面では一覧を左側パネルから折り畳み可能な画面下部のパネルへ切り替え、地図操作領域を利用者が確保できるようにする。端末のsafe areaと動的viewportへ追従し、入力欄と主要操作は44px以上のタッチ領域を持たせる。凡例も標準の`details`要素で折り畳めるようにする。
- 色だけで選択や警告を伝えず、テキスト、形状、フォーカス表示を併用する。`prefers-reduced-motion`も尊重する。

独自UIコンポーネントライブラリや画像素材は使わず、HTMLとCSSで表現する。

### 一覧、検索、絞り込みを同じクライアント状態から導出する

一覧ウィジェットにはフリーワード検索、ブランド選択、価格帯選択を置く。フリーワードは施設名、ブランド、住所、契約経路を対象に、大文字小文字と全角・半角空白の差を無視した部分一致とする。適用中の検索語と絞り込み条件をすべて満たすレコードだけを、地図と一覧の双方へ渡す。

価格帯は、現在のITS補助適用後料金を分けやすい次の固定区分とする。

- 499円以下
- 500円以上999円以下
- 1,000円以上1,499円以下
- 1,500円以上

曜日などで複数の料金がある施設は、少なくとも1つの料金が選択帯に入れば一致とし、一覧には条件を含む全料金を表示する。価格体系が区分に適さなくなったときにのみ区分を見直す。

### 基準地点と距離はブラウザ内で扱う

起動時にブラウザのGeolocation APIで現在地を取得する。許可拒否、タイムアウト、取得失敗の場合は東京駅を基準地点とする。基準地点と、その地点から最も近い絞り込み前の施設を含む境界を `fitBounds` に渡して初期表示する。

利用者が地図をクリックすると基準ピンを配置し、その後はドラッグで移動できる。基準ピンを解除すると、取得済み現在地、東京駅の順で基準地点を戻す。距離はMapLibreの球面距離計算を使用し、表示対象を昇順に並べる。現在地と任意ピンの座標はサーバーへ送信せず、ブラウザ内だけで保持する。

### 施設選択は非モーダルの詳細カードへ接続する

施設ピンと一覧行の選択は同じクライアント状態を更新し、選択中の施設を1つの詳細カードへ描画する。詳細カードには施設名、ブランド、契約経路、全料金、基準地点からの距離、住所、施設公式情報へのリンク、閉じる操作を置く。地図上で施設を続けて比較できるよう、フォーカスを閉じ込めるモーダル`dialog`は使わない。

デスクトップでは一覧と重ならない地図右下のフローティングカードとして表示する。狭い画面では施設選択時に一覧パネルを自動で折り畳み、その上へボトムシートとして表示する。一覧パネルを開いている間は地図を覆いすぎないよう詳細カードを隠し、再び一覧を折り畳むと選択中の詳細を再表示する。詳細カードを閉じても施設ピンの選択状態は維持し、同じピンまたは別のピンを選択すればカードを表示または更新する。

### 契約経路単位の公開カタログを使用する

公開JSONはカタログ全体の生成日時と、契約経路ごとの独立した施設掲載を持つ。概念上の形は次のとおりとする。

```json
{
  "schemaVersion": 1,
  "generatedAt": "2026-08-30T00:00:00Z",
  "gyms": [
    {
      "id": "konami-affiliate:provider-stable-key",
      "name": "施設名",
      "brand": "利用者向けブランド",
      "contractRoute": "konami-affiliate",
      "address": "住所",
      "location": { "longitude": 139.0, "latitude": 35.0 },
      "fees": [{ "label": "気軽に都度利用(A)", "yen": 770 }],
      "eligibilitySource": { "url": "...", "checkedAt": "2026-08-30" },
      "facilitySource": { "url": "...", "checkedAt": "2026-08-30" }
    }
  ]
}
```

`contractRoute` は `healthpia`、`konami-direct`、`konami-affiliate`、`central-series` の4値とする。`brand` は利用者が認識する施設ブランドとし、契約経路とは分ける。コナミ直営とへるすぴあは固定値、系列・提携施設は施設名に対する小さな別名表で正規化し、未知のブランドは `その他` とする。別名表は更新スクリプト内の単純な対応表とし、専用の分類サービスは作らない。

`id` は契約経路と提供元の識別子から生成し、提供元に識別子がない場合は正規化した施設名と住所からNode.js標準のハッシュで生成する。異なる契約経路では、名称、住所、座標が一致しても必ず別IDとなる。

同一座標の施設ピンはGeoJSONの地理座標を変更せず、契約経路順に小さな画面上オフセットを与える。一覧、施設ピン、3Dオーバーレイの選択を同期し、元の正確な位置と契約経路を確認できるようにする。クラスタリングは、1掲載1ピンを優先するためMVPでは行わない。

### AIを使わず公式HTMLを決定論的に処理する

週次更新はNode.jsのES Modulesスクリプトで実行する。HTTP取得にはNode.js標準 `fetch`、HTMLの表と項目抽出にはCheerioを使う。抽出、分類、正規化、料金変換は固定セレクタ、文字列正規化、明示的な対応表だけで行い、AI、LLM、AI-OCR、AIサービスを呼び出さない。クラス階層や汎用スクレイピング基盤は作らず、ソースごとの関数から共通の公開レコードへ正規化する。

- へるすぴあ: ITSページから単一施設の住所と曜日別料金を取得する。
- コナミスポーツクラブ: 公式施設検索またはそこから参照できる公式施設一覧から施設名、住所、カテゴリを取得し、ITSページのカテゴリ別本人負担額へ変換する。グランサイズは対象外とする。
- コナミ提携施設: 公式提携施設一覧から `気軽に都度利用(A)` の料金、施設名、住所を取得し、ITSページの料金表から本人負担額へ変換する。
- セントラル系列: 公式クラブ一覧の入口から `area=club_*` の都道府県別リンクを機械的に収集して重複を除き、各ページから施設名、住所、利用料を取得する。利用料はITSページの本人負担額へ明示的な対応表で変換する。公式PDFは自動処理せず、人間が件数や内容を照合する補助資料としてのみ使用する。

各関数は取得元URLと確認日をレコードへ付与する。元料金に対応するITS本人負担額が見つからない場合、未知のブランドや表記を既知ブランドへ推測で分類する場合、または期待したHTML構造を取得できない場合は、AIや推測で補完せず更新を失敗させる。ブランドの別名表にない施設は、明示された規則どおり `その他` として扱う。

PDFを主入力とする案は、表の列位置や改ページに依存するパーサーとPDF.jsが必要になるため採用しない。都道府県別HTMLは施設ごとに名称、住所、利用料がラベル付きで並び、HTMLパーサー1つで他のソースと同様に処理できる。

### 座標をバージョン管理されたキャッシュに保持する

住所から座標への変換結果は、正規化した住所をキーとするキャッシュへ保存する。週次更新では住所が新規または変更された場合だけジオコーディングし、既存住所を毎回問い合わせない。座標は、施設提供者の公式座標、バージョン管理された補正台帳、正式キャッシュ、外部ジオコーダーの順で決定する。

補正台帳は正規化した元住所をキーとし、検索用の補正住所または確定座標のいずれかと、根拠URL、確認日、補正理由を保持する。検索用住所だけを補正しても公開用データの住所は提供元の元表記を維持する。元住所が変更された場合は既存補正を自動適用せず、再確認を必要とする。補正の作成にAIや推測は使わない。

公式座標、補正台帳、正式キャッシュのいずれにも座標がない住所は、日本住所の検索精度を優先して国土地理院の地名検索APIを主候補とし、Nominatimを補助候補とする。国土地理院APIは最大20リクエスト/秒（リクエスト開始間隔50ms以上）、Nominatimは最大1リクエスト/秒で問い合わせ、結果を必ずキャッシュする。検索結果は、元住所または補正台帳の検索用住所から固定規則で抽出した都道府県、市区町村、町域が返却住所と一致する場合だけ採用する。一致する結果がない場合や候補が矛盾する場合は推測で採用しない。

ジオコーディングできない新規住所がある場合は、施設名、契約経路、元住所、施設情報の参照先、取得した候補、および各候補の棄却理由を持つ非公開の失敗レポートを生成する。未解決の掲載を黙って除外せず、不完全な位置情報を公開しないで更新を失敗させる。失敗レポートを基に公式施設ページなどを人手で照合し、根拠付きの補正を補正台帳へ追加してから再生成する。

同じ住所群を再問い合わせしないよう、住所要素の一致を確認できた座標だけをGit管理および公開対象外の一時キャッシュへ保存し、次回実行で正式キャッシュと合わせて再利用する。正式キャッシュの値を一時キャッシュより優先し、全住所の座標化とカタログ検証に成功した場合だけ公開JSONと正式キャッシュを置き換えて一時キャッシュを削除する。失敗時は公開JSON、正式キャッシュ、確認日を変更しない。利用量や利用条件が公開サービスに適さなくなった時点で、有償プロバイダーまたは自己運用へ切り替える。

### 検証を通過した更新だけを公開する

更新スクリプトは少なくとも次を検証する。

- 必須項目、URL、確認日、料金、緯度経度の形式と範囲
- IDの一意性と、契約経路が許可された4値であること
- 料金が0以上の整数であり、元料金からITS本人負担額への対応が存在すること
- 各ソースの取得件数が0件でなく、直前データから不自然に急減していないこと
- セントラルの都道府県別リンクを重複なく収集でき、期待する都道府県を欠いていないこと
- コナミ直営にグランサイズが含まれないこと
- 各取得関数が保存した最小のHTMLサンプルから期待レコードを生成できること

テストにはNode.js標準の `node:test` を使い、別のテストフレームワークやJSONスキーマライブラリは追加しない。いずれかの取得、変換、座標化、検証に失敗した場合は非0で終了し、公開JSON、確認日、Pages配信を更新しない。

### GitHub Actionsで更新と配信を行う

1つのGitHub Actions workflowでテスト、データ更新、ビルド、GitHub Pages配信を行う。通常のpushに加え、月曜と木曜のJST 03:17に実行し、`workflow_dispatch` でも手動実行できるようにする。毎時0分を避け、週1回の取りこぼしがあっても次回まで7日を超えにくい間隔にする。

定期実行または手動実行では、検証済みの公開JSONと座標キャッシュに差分がある場合だけ自動コミットし、同じ実行でビルドした成果物をPagesへ配信する。確認日は成功時に更新されるため、通常は週2回データコミットが作成され、公式情報との照合履歴として利用できる。

サイトのステータスバーには最も古い参照先の確認日を表示し、7日を超えた場合は `DATA STALE` と明記する。

## Risks / Trade-offs

- [公式HTMLの構造変更で抽出が壊れる] → ソース別のサンプルテスト、件数急減検知、必須項目検証を行い、失敗時はAIや推測で補完せず直前のPages配信を維持する。
- [GitHub Actionsの定期実行が遅延、欠落、無効化される] → 週2回を毎時0分以外に設定し、手動実行を用意し、サイト上で7日超過を表示する。
- [OpenFreeMapは可用性保証がない] → MapLibre互換性を維持し、スタイルURLの差し替えだけで別プロバイダーへ移行できるようにする。
- [国土地理院APIとNominatimは可用性保証がなく、検索結果が不正確な場合がある] → 新規・変更住所だけを国土地理院APIは最大20リクエスト/秒、Nominatimは最大1リクエスト/秒で問い合わせ、住所要素が一致する結果だけを永続キャッシュし、一致しない場合は施設名と棄却理由を含む失敗レポートを生成して根拠付き補正を行う。
- [旧行政区名、表記揺れ、提供元の誤記が同じ入力では恒久的に座標化できない] → 元住所を表示用に保持したまま、根拠URL、確認日、理由を持つ補正住所または確定座標をバージョン管理し、元住所の変更時は再確認する。
- [大量の新規住所の一部が解決できず、再実行のたびに解決済み住所まで問い合わせる] → 検証済み座標を非公開の一時キャッシュへ保存して再利用し、全件成功時だけ正式キャッシュへ反映する。
- [同一座標の複数ピンをずらすと見かけの位置がわずかに変わる] → データの緯度経度は変更せず画面表示だけをずらし、選択時に同一地点の掲載であることを確認できるようにする。
- [サイバーパンク表現や常時アニメーションが可読性、操作性、描画性能を損なう] → 装飾をCSSの`transform`と`opacity`中心に限定し、操作部を動かさず、十分なコントラスト、キーボードフォーカス、文字ラベル、`prefers-reduced-motion`を優先する。
- [多数の施設ピンと3Dラベルで描画が重くなる] → 施設ピンと3Dガイドを同じGeoJSON sourceのsymbolレイヤーで一括描画し、DOM要素を施設数だけ生成しない。
- [モバイル端末でHUDが地図を覆い、アニメーションが電池と描画性能を消費する] → 一覧と凡例を折り畳み可能にし、モバイル幅では地図走査ビームを停止して地図と操作へ描画資源を優先する。
- [施設詳細カードが地図や一覧を覆い比較を妨げる] → カードを非モーダルにし、デスクトップでは一覧と反対側、モバイルでは折り畳んだ一覧の上へ配置し、閉じても選択状態を維持する。
- [自動コミットが保護ブランチ設定と競合する] → 初期運用ではActionsからのデータ更新を許可し、保護ルールが必要になった時点でデータ用ブランチまたは別の永続化先を検討する。

## Migration Plan

1. ViteとMapLibreによる静的画面、公開JSONの型、最小のサンプルデータを作る。
2. ソース別の取得関数、座標キャッシュ、失敗レポート、補正台帳、検証テストを追加し、未解決住所を根拠付きで補正してから初回カタログの件数、料金、位置を確認する。
3. GitHub PagesとActionsを有効化し、手動実行で更新、コミット、ビルド、配信を通してから定期実行を開始する。
4. 公開後は最終確認日とActions失敗を確認する。失敗時は直前のPages配信を維持し、修正後に手動実行する。

データを巻き戻す場合は、問題のある自動更新コミットをrevertし、通常のPagesビルドを再実行する。地図サービスに問題がある場合はスタイルURLを以前の値または代替サービスへ戻して再配信する。
